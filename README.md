# Banana Blast 3D

A 2-4 player online 3D bomb-arena party game. Real-time 3D with Three.js, server-authoritative multiplayer with Node.js, Express and Socket.IO. Works on phones and desktop browsers.

> **Reference note.** The game that prompted this project, *BOMBANANA!* (Lefto Studio / TARK, Steam, released 2 Sept 2026), is a **3-player co-op bomb-defusal puzzle game** (blind, deaf and mute monkeys defuse bombs together). It is *not* an arena bomber. This project is therefore an **original** game that follows the arena-battle brief, only borrowing the banana/monkey-and-bombs theme. No assets, code, names of levels or branding from BOMBANANA! are used.

## What's in the box

- Server-authoritative simulation (`src/game.js`): movement, collisions, bombs, chain reactions, flames, crates, 7 power-ups, win/draw/time-up logic. Clients only send *intent* (move direction, "bomb", "detonate", "peel").
- Rooms (`src/rooms.js`): 4-letter codes, 2-4 players, ready states, host start, rematch, disconnect grace period with secure token-based reconnection.
- Three.js client (`public/js/`): low-poly procedural art (no model files), danger-tile overlay, particles, shake, adaptive resolution, WebAudio sound effects (no audio files).
- Mobile UI: floating virtual joystick, bomb / boom / peel buttons, landscape + portrait, safe-area aware, zoom and scroll blocked while playing.

## Run it on a computer

```bash
npm install
npm start          # listens on PORT (default 3000)
```

Open `http://localhost:3000` on that computer. Friends on **other phones cannot use `localhost`**: they need a public URL (see hosting below) or your computer's LAN address on the same Wi-Fi.

Other commands: `npm test` (44 automated tests of the server logic) and `npm run check` (static consistency checks).

## Hosting for friends on separate phones

Opening `index.html` directly, or using GitHub Pages / any static-only host, **does not work**: the game needs the Node.js server for rooms and the match simulation. Acode (or any phone code editor) can only *edit* files; it cannot run the server. You need a Node.js host.

### Example: Render (free web service)

1. Put this folder in a GitHub repository (the GitHub mobile site or the Acode Git feature can upload it).
2. On render.com create a **New > Web Service**, connect the repo.
3. Settings: Runtime **Node**, Build command `npm install`, Start command `npm start`, Health check path `/health`.
4. Choose the Free instance type, then deploy. When it says *Live*, open the `https://<name>.onrender.com` URL.
5. Share that URL (or the invite link from the lobby) with friends.

Free-tier facts I checked on Render's docs (October 2026; re-check before relying on them): free web services spin down after 15 minutes without inbound traffic and take roughly half a minute to wake up; the filesystem is ephemeral and Render may restart a free service at any time. Because rooms live in server memory, **a restart ends all rooms and matches**. Open the URL once a minute before playing so it is awake. Other Node hosts (Railway, Fly.io, Koyeb, a small VPS, etc.) also work; I did not verify their current pricing or limits, so check each one. The host must support long-lived WebSocket connections and give you an HTTPS URL.

### Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | 3000 | Set automatically by most hosts |
| `ALLOWED_ORIGIN` | empty | Only needed if the page is served from a different origin than the server |
| `MAX_ROOMS` | 200 | Cap on simultaneous rooms |
| `RECONNECT_GRACE_MS` | 20000 | How long a disconnected player keeps their slot mid-match |

No API keys or secrets are used anywhere.

## Playing

1. Everyone opens the same HTTPS URL and enters a nickname.
2. One player taps **Create room** and shares the 4-character code (or **Copy invite link**).
3. Others type the code and tap **Join room**, then **Ready**. The host taps **Start match** (needs 2+ players, everyone else ready).
4. Controls: drag on the left half (or WASD/arrows) to move; **Bomb** / Space; **Boom** / E detonates (needs the detonator power-up); **Peel** / Q drops a banana trap; walk into a bomb with Kick to push it.

## Rules and design decisions

- Arena 13 x 11 cells, borders and every even/even cell are indestructible; crates (72% of free cells) are generated by the server from a seed and sent to all clients. Spawn corners keep an L-shaped crate-free zone plus two escape cells.
- Fuse 2.5 s. Blast is a cross, range 2 at start. Walls stop it; a crate is destroyed and also stops it; a bomb in the path is chained.
- **Order of operations** for simultaneous explosions is documented at the top of `src/game.js`: all due bombs plus their chain reactions are collected first, all blast shapes use the layout from the start of the step, then damage is applied once per explosion group per player.
- Flames last 0.6 s and cannot be walked into unharmed. A shield absorbs one explosion and grants 0.7 s of invulnerability.
- Power-ups drop from destroyed crates (38%): extra bomb, bigger blast, speed boost (8 s), shield, remote detonator (3 charges), banana peel (slip for ~1 s, 12 s lifetime), bomb kick.
- Match limit 3 minutes. Last player alive wins; everyone dying in the same server step is a draw; if time runs out with several alive it is a draw between them.
- Eliminated players spectate. Respawn is not part of this mode.
- **Disconnects:** in lobby/results you are removed instantly. In a match you stand still and vulnerable for 20 s and can resume with your private token (stored in the tab's sessionStorage); after that you are eliminated. Leaving on purpose eliminates you immediately. The host role passes to the next connected player.

## Project layout

```
banana-blast-3d/
  package.json        dependencies (express, socket.io, three) and scripts
  server.js           Express + Socket.IO wiring, validation, rate limits, /health
  .env.example        documented environment variables
  src/config.js       all gameplay constants
  src/game.js         authoritative simulation (pure logic, no I/O)
  src/rooms.js        rooms, lobby, match lifecycle, reconnection
  public/index.html   screens and modals
  public/style.css    responsive mobile-first styling
  public/js/main.js   client controller: networking, screens, HUD, settings
  public/js/scene.js  Three.js arena, characters, effects, camera
  public/js/input.js  keyboard, joystick, buttons
  public/js/audio.js  generated sound effects
  public/assets/      (empty; everything is procedural)
  scripts/static-check.js   consistency checks
  test/               node:test suites (game logic, rooms, server wiring)
```

Why extra files beyond the suggested structure: `src/` keeps the testable simulation separate from the socket glue, and the client is split into four ES modules (one `<script type="module">`; Three.js is resolved through an import map to `/vendor/three/`, which the server serves from the `three` npm package, so there is no CDN dependency).

## Known limitations

- **Not tested in a real browser or on real phones** by the author of this code (see the checklist in the hand-off message). Rendering, touch controls and audio are written carefully but unverified. Please report anything odd.
- No client-side movement prediction: your own banana follows the server position with smoothing, so on poor connections movement feels slightly delayed.
- State lives in memory: server restart = all rooms lost. Reconnect works only for the same tab session (sessionStorage) and only during a match.
- One map layout (procedurally seeded crates). No spectators joining mid-match, no chat, no matchmaking beyond private codes.
- The red danger overlay is an approximation for display; the server alone decides hits.
